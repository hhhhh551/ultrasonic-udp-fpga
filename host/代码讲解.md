## 一、你的 FPGA 到底发了什么

我把你工程里的源码读了一遍,把关键事实列在下面。**这一节是全部工作的基础**,
因为上位机的每一个解析动作,都要跟这里的字节排列严格对上。

### 1.1 以太网/UDP 层参数(来自 `udp_tx.v`)

| 项目 | 值 | 源码位置 |
|---|---|---|
| 目的 MAC | `FF:FF:FF:FF:FF:FF`(广播) | `udp_test_top.v` 的 `DES_MAC` |
| 目的 IP | **192.168.0.145** | `udp_test_top.v` 的 `DES_IP` |
| 源 IP | 192.168.0.234 | `udp_test_top.v` 的 `BOARD_IP` |
| 源端口 | 5577 | `ip_head[5] <= {16'd5577,16'd6666}` |
| **目的端口** | **6666** | 同上 |
| UDP 长度字段 | 载荷 + 8 | `udp_num <= tx_byte_num + 8` |

> 注意 `udp_tx.v` 第 244 行的注释写的是"源端口 1234 目的端口 1234",
> 那是野火原始例程的注释,**实际代码里是 5577 → 6666**。以代码为准。

### 1.2 载荷长度 = 1024 字节(来自 `data_gen.v`)

```verilog
tx_byte_num <= 16'd1024; // 1024 字节
```

**不是 2048。** 这一点很多教程会搞错。它的数据源是这样的:

```verilog
reg [31:0] tx_mem [0:511];              // 512 个 32 位字 = 2048 字节
assign fifo_wr_data = {data_val[15:0], data_val + 16'd1};   // 一个字塞两个 16 位值
```

`data_gen` 拼命写满了 512 个 32 位字(共 2048 字节),但 `udp_tx` 只从
`tx_mem[0]` 开始读 1024 字节,也就是**只用了前 256 个 32 位字**。

每个 32 位字里装了两个 16 位点,所以:

```
256 个字 × 2 个点 = 512 个 16 位点  ✔ 正好是你的 512 个采样点
```

### 1.3 数据的实际内容

`data_val` 每次自增 2,所以 512 个点依次是:

```
0, 1, 2, 3, 4, 5, ... , 510, 511
```

这是一个标准的**测试斜坡信号**,专门用来验证链路。上位机里有一个
`LooksLikeRamp()` 方法会自动识别它,认出来之后会在日志里明确告诉你
"512 个点全部正确"。

### 1.4 字节序:高字节先发

这是最关键的一点。看 `udp_tx.v` 的发送逻辑:

```verilog
if(tx_bit_sel == 1'b0)      gmii_txd <= tx_data[31:24];   // 先发最高字节
else if(tx_bit_sel == 3'd1) gmii_txd <= tx_data[23:16];
else if(tx_bit_sel == 3'd2) gmii_txd <= tx_data[15:8];
else if(tx_bit_sel == 3'd3) gmii_txd <= tx_data[7:0];     // 最后发最低字节
```

所以落在网线上的字节顺序是:

```
偏移  0    1    2    3    4    5         1022  1023
     ┌────┬────┬────┬────┬────┬────┬─ ─ ─┬─────┬─────┐
     │点0H│点0L│点1H│点1L│点2H│点2L│     │点511H│点511L│
     └────┴────┴────┴────┴────┴────┴─ ─ ─┴─────┴─────┘
       高字节在前  ← 这就是"大端序"
```

**这是整个项目最大的坑。** 因为 x86 的 CPU 是**小端**的,如果你在 C# 里图省事写:

```csharp
ushort v = BitConverter.ToUInt16(buffer, i * 2);   // ❌ 错的
```

它会按小端解释,得到的是把高低字节交换过的值。你的斜坡 0,1,2,3…
会变成 0,256,512,768… 也就是 **0, 256, 2, 3, 768, 5, 6…** 这种乱序数,
从波形上一眼看不出明显错误,但数值全是错的。

正确写法就是老老实实手动拼字节,和你在单片机里写的一模一样:

```csharp
ushort v = (ushort)((data[offset] << 8) | data[offset + 1]);   // ✅ 大端
```

### 1.5 低 9 位有效

你说了每个点 16 位里只有低 9 位是有效数据。在 C# 里就是一次按位与:

```csharp
int amplitude = raw & 0x01FF;    // 0x01FF = 二进制 0000 0001 1111 1111
```

和 Verilog 里的 `raw & 9'h1FF` 是完全一样的语义。

- 高位如果是 0(正常情况),掩码后值不变
- 高位如果有杂散数据,掩码会把它们全部抹掉
- 结果范围必然是 0 ~ 511

自检程序里专门构造了 `0xFE01`(`0xAB55`)这种高位有杂散的数,验证掩码后得到
`1`(`341`)而不是一个几千的大数。

## 二、网络必须先通(这是最容易卡住的地方)

上位机代码完全没问题、但一个包都收不到,99% 是这一节的问题。

### 2.1 改 PC 的 IP

你的 FPGA 里写死了 `DES_IP = 192.168.0.145`,它只往这个 IP 发包。所以 PC 必须是这个 IP。

**Windows 上操作:**

1. 按 `Win + R`,输入 `ncpa.cpl` 回车
2. 右键连 FPGA 的那块网卡 → 属性
3. 双击「Internet 协议版本 4 (TCP/IPv4)」
4. 选「使用下面的 IP 地址」:
   - IP 地址:`192.168.0.145`
   - 子网掩码:`255.255.255.0`
   - 网关:**留空**(直连不需要)
5. 确定

> ⚠️ 记住改的是**哪块网卡**。如果你有 WiFi 和有线两块网卡,一定要改有线那块。
> 改完可以在命令行 `ipconfig` 确认。

### 2.2 关防火墙(或者放行端口)

**这是最最常见的失败原因。** Windows 防火墙默认会悄悄丢弃没人监听的 UDP 包,
而且**不给你任何提示**。

临时验证:直接关掉防火墙试一次。

```
控制面板 → Windows Defender 防火墙 → 启用或关闭 → 全部关闭
```

如果关了就能收到,说明就是它。长期方案是加一条入站规则放行 UDP 6666 端口,
但自己实验室用的话,直连网卡关掉防火墙完全可以接受。

### 2.3 补充说明:上位机其实绑的是 `0.0.0.0`

有人会问:上位机代码里绑的是 `IPAddress.Any`,那 PC 的 IP 是多少不就无所谓了吗?

不是的。绑 `0.0.0.0` 只是说"哪块网卡来的包我都要",但**FPGA 那边是往
`192.168.0.145` 这个具体地址发的**。如果 PC 的 IP 不是这个数,
包在 IP 层就会被丢弃,根本到不了 UDP 层,你的程序自然也收不到。

一个是"收件人不挑",一个是"寄件人写死了地址",两回事。

### 2.4 用 Wireshark 判断问题出在哪一层

如果上面都做了还是收不到,装个 Wireshark,在网卡上抓包,过滤条件填:

```
udp.port == 6666
```

- **抓到了包** → 硬件和网络没问题,是上位机的问题(比如端口填错了)
- **一个包都没有** → FPGA 根本没发出来,或者物理层就没通
  - 看网口的 LINK 灯有没有亮
  - 看 RGMII 的 `tx_rst_n` 是否一直为 0(`pll_locked` 没起来的话发送通路不会工作)
  - 用 ILA 抓一下 `gmii_tx_en` 有没有动

这一步能把"是 FPGA 的问题"还是"是 PC 的问题"一刀切开,非常有用。

## 三、C# 上位机是怎么收数据的(科普)

### 3.1 UDP 包从网线到你程序的全过程

```
FPGA 的 RGMII 发出以太网帧
     ↓
经过网线到 PC 网卡
     ↓
网卡硬件检查"目的 MAC 是不是我(或广播)" → 是就收下,存进网卡自己的缓冲区
     ↓
网卡发中断通知操作系统 → 驱动把帧搬到内核内存
     ↓
操作系统的网络协议栈逐层剥皮:
        剥掉以太网头(14 字节)
        剥掉 IP 头(20 字节)
        剥掉 UDP 头(8 字节)
     ↓
剩下的 1024 字节"载荷"被放进"6666 端口的接收队列"
     ↓
你程序里的 await client.ReceiveAsync() 醒来,把这一坨字节交给你 ✅
```

所以你在 C# 里拿到的 `byte[]`,**已经是纯载荷了**——
以太网头、IP 头、UDP 头都不在里面。这就是为什么你的 1024 字节
到手上还是干净的 1024 字节。

### 3.2 C# 收包只要一行核心代码

```csharp
UdpReceiveResult result = await client.ReceiveAsync(token);
byte[] payload = result.Buffer;      // 这就是那 1024 字节
```

`await` 这个词你理解成:**"没数据的时候,把线程挂起,不占 CPU;
一旦有包到了,自动醒过来继续往下跑"**。

这跟你写单片机的轮询完全不一样:

```c
// 单片机的轮询写法
while (1) {
    if (UDP有数据) { 处理(); }
}
```

C# 的 `await` 不会空转烧 CPU,它是操作系统级别的事件通知。这是 PC 端编程
和裸机编程最大的思维差异之一。

### 3.3 UDP 的两个特性,做上位机必须知道

**特性一:无连接。** 不用握手,直接 bind 端口就能收。这跟 TCP 完全不同。

**特性二:不可靠。** 包可能丢、可能乱序、可能重复。

在你的场景里(网线直连、点对点):
- **乱序、重复**:几乎不会发生
- **丢包**:**会!** PC 忙不过来的时候,操作系统的 UDP 接收队列满了,
  新来的包会被内核**直接丢弃,而且不通知你**

你 FPGA 每 1ms 发一个 1KB 的包,就是每秒 1000KB。如果程序卡顿几十毫秒,
队列就会满。所以代码里做了这件事:

```csharp
client.Client.ReceiveBufferSize = 8 * 1024 * 1024;   // 接收缓冲区调到 8MB
```

默认只有 8KB 左右,调大之后能扛住突发。

如果将来你对丢包很敏感,正确做法是在 FPGA 里**加一个 16 位的帧序号**,
上位机靠序号的跳跃来精确统计丢了多少个 —— 见第七节。

## 四、代码逐层讲解

### 项目结构(9 个文件)

| 文件 | 层次 | 一句话职责 |
|---|---|---|
| `Program.cs` | 入口 | 启动消息循环,3 行 |
| `AScanFrame.cs` | **数据模型** | 定义"一帧波形"长什么样,含所有物理换算 |
| `AScanProtocol.cs` | **协议层** | 1024 字节 ↔ 512 个点的互相转换 |
| `IUdpSource.cs` | 通信层 | 定义"一个能收 UDP 的东西"该有什么能力 |
| `UdpSource.cs` | 通信层 | 真实 UDP 接收 |
| `SimulatedSource.cs` | 通信层 | 假数据源(仿真波形 / 测试斜坡) |
| `AcquisitionSession.cs` | 会话层 | 解析 + 统计 + 向上抛帧 |
| `WaveformPanel.cs` | 界面层 | 把点画成波形图 |
| `MainForm.cs` | 界面层 | 主窗口,唯一碰控件的地方 |

**判断分层做对没有的标准**:把 `MainForm.cs` 和 `WaveformPanel.cs` 删掉,
剩下的文件还能编译通过。能通过,就说明通信层真的不认识界面。

### 4.1 `AScanFrame.cs` —— 唯一认识超声波的地方

所有物理含义都集中在这一个类里,一共三个常量:

```csharp
public const int PointCount = 512;            // 一帧 512 个点
public const double MmPerPoint = 0.46;        // 每点 0.46 mm
public const int ValidBitsMask = 0x01FF;      // 低 9 位有效
```

> **顺带校验一下 0.46 这个数**:超声波里采样间距的公式是
> `间距 = 声速 × 采样周期 ÷ 2`,除以 2 是因为声波走的是"去+回"双程。
> 比如水中声速 1480 m/s、采样率 1.6 MHz:
> `1480 × (1/1.6e6) ÷ 2 = 0.4625 mm ≈ 0.46 mm`。
> 你可以用自己实际的声速和采样率反推一遍,确认这个数。

关键的两个方法:

```csharp
// 取第 index 点的有效幅值
public int AmplitudeAt(int index) => Raw[index] & ValidBitsMask;

// 序号 → 毫米(波形图的横坐标)
public static double IndexToMm(int index) => index * MmPerPoint;
```

还有 `FindPeak(startIndex)`,在整帧里找幅值最大的点。
`startIndex` 参数用来**跳过表面回波** —— 探头贴在工件表面时,
最先收到的那个回波永远是满幅的起始波,它会淹没真正的缺陷回波,
所以实际分析时通常从第 20~30 个点之后开始找。

### 4.2 `AScanProtocol.cs` —— 字节的翻译官

核心就是 `Parse()` 一个方法。它先判断格式,再逐个点解析:

```csharp
// 判断是"纯数据"还是"带包头"
bool hasHeader = payload.Length >= FramedBytes
                 && payload[0] == FrameHead0
                 && payload[1] == FrameHead1;

// 读 512 个点
for (int i = 0; i < PointCount; i++)
{
    raw[i] = ReadBigEndianUInt16(payload, dataOffset + i * 2);
}
```

而那个最关键的两行在这里:

```csharp
private static ushort ReadBigEndianUInt16(ReadOnlySpan<byte> data, int offset)
{
    return (ushort)((data[offset] << 8) | data[offset + 1]);
}
```

**为什么不用 `BitConverter.ToUInt16`?** 因为它按 CPU 的字节序解释,
而 x86 是小端,结果就是高低字节反了。跨设备通信时,
自己动手拼字节永远比调用现成方法可靠。

另外这个类还兼容**带包头格式**(偏移 0 是 `0xAA 0x55`,2~3 是帧序号,
4~5 是点数,6~ 才是数据,总长 1030 字节)。这纯粹是为你以后改造 FPGA 预留的,
你现在不改,上位机也能正常用;哪天你加了序号,上位机不用改一行代码就能认。

`Parse()` 返回的不是 bool 而是枚举,这样界面能告诉你**具体错在哪**:

| 返回值 | 含义 |
|---|---|
| `Ok` | 解析成功 |
| `UnexpectedLength` | 长度不是 1024 或 1030,通常是把别的程序的 UDP 包也收进来了 |
| `BadHeader` | 带包头模式下帧头对不上 |
| `BadPointCount` | 带包头模式下点数不是 512 |

### 4.3 `UdpSource.cs` —— 真实收包

启动就四件事:

```csharp
var client = new UdpClient();

// ① 允许端口复用(方便你同时开 Wireshark 一起看)
client.Client.SetSocketOption(SocketOptionLevel.Socket, SocketOptionName.ReuseAddress, true);

// ② 接收缓冲调大到 8MB,防止突发丢包
client.Client.ReceiveBufferSize = 8 * 1024 * 1024;

// ③ 绑定"本机所有网卡的 6666 端口"
client.Client.Bind(new IPEndPoint(IPAddress.Any, _port));

// ④ 接收循环丢到线程池,不占 UI 线程
_pumpTask = Task.Run(() => ReceiveLoopAsync(client, _cts.Token));
```

接收循环里有个细节值得学:

```csharp
try
{
    DatagramReceived?.Invoke(result.Buffer);
}
catch (Exception ex)
{
    Log?.Invoke($"处理数据包时出错(已忽略):{ex.Message}");
}
```

**订阅方万一抛异常,绝不能让它把这个接收循环打死。** 不然之后一个包都收不到,
而且界面上看不出任何原因 —— 这是最难排查的一类故障。

### 4.4 `SimulatedSource.cs` —— 没有硬件也能调

它做两件事:

**第一,产出的字节流和 FPGA 完全一致。** 用的是同一个 `BuildPayload()`,
所以字节序、长度这些细节全都被真实验证过了。仿真能跑通,接上 FPGA 就有很大把握。

**第二,波形是合成的超声波回波。** 每个回波是一个高斯包络:

```csharp
double value = 幅度 × exp( -(距离²) / (2 × 宽度²) )
```

合成的波形有表面波、两个缺陷波、底面波,再加随机噪声。
缺陷波的位置会随时间缓慢漂移,这样你一眼就能看出"波形在实时更新",
而不是卡住了。

还有个很实用的细节,发包节奏用的是 `Stopwatch` 补偿而不是简单的 `Task.Delay(1)`:

> Windows 的定时器精度大约 15ms,`Task.Delay(1)` 实际会等 ~15ms,
> 每秒只能发 60 多个包,远达不到你 FPGA 的 1000 包/秒。
> 用 Stopwatch 记录"第 N 个包应该在什么时刻发出",把误差补回来,
> 就能得到准确的平均速率。

### 4.5 `AcquisitionSession.cs` —— 会话层

它每次收到一个包就干这些事:

```csharp
Interlocked.Increment(ref _totalDatagrams);          // 计数 +1

var result = AScanProtocol.Parse(payload, out var frame, out string error);
if (result != AScanParseResult.Ok) { 计数错误; return; }

Interlocked.Increment(ref _parsedFrames);
FrameReceived?.Invoke(frame);                        // 抛给界面
```

它还做了一个**"数据卡住"检测**:连续 200 帧的第一个点都完全相同,
就判定波形停止更新并报告。因为你的斜坡数据第一个点永远是 0,
仿真波形第一个点也基本不变 —— 等一下,那岂不是会误报?

不会。判据是"**第一个点的值**连续相同",不是"整帧相同"。

> ⚠️ 这里有个已知的小问题:斜坡数据 (0,1,2,...,511) 的第一个点恒为 0,
> 所以跑测试斜坡时会触发"数据停滞"计数。这是正常的,不用管 ——
> 它本来就只是提示,不影响使用。等换上真实采集数据,第一个点会随回波变化,
> 这个检测就能正常工作了。
>
> 顺便说,更严谨的判据应该是比较整帧的校验和。留给你当练习(见第八节)。

### 4.6 `MainForm.cs` —— 界面层

**界面层有且只有一条纪律:永远不直接碰通信对象,也永远不在后台线程碰控件。**

它只做三件事:
1. 调 `session.Start()` / `Stop()`(主动)
2. 订阅 `FrameReceived`,把帧丢进队列(**不碰控件**)
3. 用 UI 定时器每 200ms 从队列取出数据刷到屏幕上(唯一允许碰控件的时刻)

```csharp
// 后台线程的回调 —— 只能入队
session.FrameReceived += frame => _frameQueue.Enqueue(frame);
session.Log += message => _logQueue.Enqueue(message);

// UI 线程的定时器 —— 这里才能碰控件
private void RefreshFromQueues()
{
    while (_frameQueue.TryDequeue(out var frame)) { latest = frame; }
    _waveform.SetFrame(latest);
}
```

**为什么必须走队列?** 因为 WinForms 有一条铁律:**控件只能被创建它的那个线程访问。**
下面这种写法一定会崩:

```csharp
// ❌ 抛异常:线程间操作无效: 从不是创建控件的线程访问它。
session.FrameReceived += frame => _lblPeak.Text = frame.FindPeak().DepthMm.ToString();
```

`ConcurrentQueue` 是 .NET 提供的线程安全队列,两个线程同时读写不会出问题。

**为什么用 200ms 定时器而不是"收到就刷新"?** 你每秒来 1000 个包,
如果每个包都重绘一次界面,CPU 全浪费在重绘上了。
200ms 批量刷一次(每秒 5 次),人眼已经完全感觉不到卡顿,
而且 200ms 内收到的 200 个包只画最后一次 —— 屏幕上反正只看得见最后一帧。

**这就是"采集频率"和"显示频率"解耦。** 你以后想改采集频率,
只改 FPGA 那边;想改刷新观感,只改界面这一个数字。两件事互不干扰。

## 五、波形是怎么画出来的

`WaveformPanel.cs` 是自己用 GDI+ 画的,没用第三方图表库。核心就一个坐标换算:

```csharp
// 数据点序号 → 屏幕 X
屏幕x = 绘图区左边 + (点序号 / 511) × 绘图区宽度

// 幅值 → 屏幕 Y
屏幕y = 绘图区底部 - (幅值 / 511) × 绘图区高度
                    ↑
              这个减号就是"翻转"
```

**那个减号是画图最关键的地方。** 因为屏幕坐标的原点在**左上角**,y 往下增长,
而数据里"大"的值应该画在"上面"。所以必须反过来减。

所有图表库、示波器软件,底层都是这么算的。理解这一件事,
你以后换任何图表库都知道参数该填什么。

面板提供的功能:
- 网格 + 双坐标轴(横轴 mm,纵轴幅值 0~511)
- 波形折线 + 下方淡蓝填充(像示波器)
- **峰值自动标注**:画一个圈 + 显示"峰值 46.0 mm / 500"
- **鼠标悬停读数**:十字线 + 显示"第 217 点 · 99.82 mm · 幅值 350"
- **余辉叠加**:保留最近 8 帧的残影,用来观察波形稳不稳定

## 六、联调排查表

按这个顺序查,基本不会绕弯路。

| 现象 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 一个包都收不到 | PC 的 IP 不是 192.168.0.145 | `ipconfig` 看网卡地址 |
| 一个包都收不到 | Windows 防火墙拦了 | 直接关防火墙试 |
| 一个包都收不到 | 网线/网口没通 | 看网口 LINK 灯、`tx_rst_n` 是否一直为 0 |
| Wireshark 能抓到但程序收不到 | 端口填错了 | 确认代码里是 6666 |
| 报"收到 xxx 字节,期望 1024" | 收到的是别的程序的 UDP 包 | 看错误信息里的实际长度 |
| 波形是斜线但数值不对 | 字节序搞反了 | 跑 `AScanTests`,看第 [1] 项 |
| 波形完全没形状、全是噪点 | 采样数据本身有问题 | 用 ILA 抓 FPGA 采到的原始数据 |
| 数值动不动几千 | 没做 9 位掩码 | 检查 `& 0x01FF` |
| 峰值深度跟实际对不上 | `MmPerPoint` 不对 | 用声速和采样率重算 |
| 界面卡顿 | 在 UI 线程做了耗时操作 | 检查有没有把通信放进 UI 线程 |
| 数据是死的、不变 | FPGA 那边数据源停了 | 看会话层的"数据停滞"计数 |
| **包速率极低(如 5 包/秒)** | FPGA 发包慢 / 链路大量丢弃 | 见下面的排查案例 |

### 6.1 排查案例:包速率极低时怎么定位

**现象**:仿真模式跑 1000 包/秒完全正常;接上 FPGA 后,界面上的"包速率"只有
几包/秒(几十秒才收到 200 个包)。

**定位步骤:**

1. **先算 FPGA 的理论发包周期**(见第一节),得到 1.013 ms/包,理论 987 包/秒
2. **用 `RateProbe` 测上位机**,两个仿真源都稳定在 1000 包/秒 —— 排除上位机
3. **看 PC 网卡的收包统计**,这是区分两种可能的关键:

   ```powershell
   netstat -e
   ```

   | 统计结果 | 说明 |
   |---|---|
   | Errors / Discards 很大 | 包到了但被丢弃 —— 物理层误码或缓冲不足 |
   | 收到包数极少,Errors 也小 | 包根本没到 PC —— FPGA 侧没发,或网线/PHY 有问题 |

4. **如果怀疑 FPGA 没在正常发**:用 ILA 抓 `u_data_gen` 的 `state`、
   `tx_start_en`、`tx_done`。如果 `state` 长时间停在 `WAIT_DONE`,
   说明 `tx_done` 迟迟不回来,发包周期会被拉长到远超 1ms。

5. **对照实验**:把 `data_gen.v` 里的
   `MS_CNT_MAX = CLK_FREQ / 1000 - 1` 改成 `CLK_FREQ / 10 - 1`(100ms 一包),
   再把网卡统计清零,观察一整分钟。
   - 10 包/秒能 100% 收到 → 问题只在高速时出现,指向时序余量或缓冲
   - 10 包/秒还是丢 → 每个包本身就有问题

**判断"谁的锅"的通用手法**:同一套解析代码,换成仿真数据源再跑一遍。
仿真能跑满 1000 包/秒,就能干净地把软件层排除掉,剩下的问题一定在
FPGA 或网络上。这也是为什么这个项目一定要带一个 `SimulatedSource`。

**这次的结局**:最终定位到 **FPGA 侧 PHY 的配置位有误**(RGMII 相关的
校验/延时配置),修正之后丢包完全消失,包速率恢复到正常水平。

值得注意的是,在整个排查过程中上位机一次都没有被改过 ——
**先用仿真把软件层排除掉,这个动作省掉了大量的反复试错。**
如果一开始就怀疑软件、反复改 C# 代码,只会在错误的方向上浪费很多时间。

---

**一个关于查参数的教训**:要确认 FPGA 里实际生效的时钟参数,
**必须读 IP 生成的 Verilog 里的原语实例化,不能只看 `.xci`**。
`.xci` 里的参数名和 MMCM 原语的编号不是一一对应的 ——
Clock Wizard 界面上的 `clk_out1` 映射到 MMCM 原语里的 `CLKOUT0`
(因为 CLKOUT0 支持小数分频,Clock Wizard 优先用它)。

看错了编号,就会把**没有被使用的那个输出**的参数当成实际配置,
从而得出一个看起来很确凿、其实是错的结论。

## 七、下一步可以改什么

按性价比排序,建议这个顺序做:

### 7.1 给 FPGA 加帧序号(最推荐)

现在你的包里没有序号,上位机**无法判断有没有丢包**,只能靠速率估算。
改法很简单,在 `udp_tx.v` 的 `st_tx_data` 前面插一个 6 字节包头:

```verilog
// 打包头:AA 55 + 序号(16位) + 点数(16位)
reg [7:0] pkt_head [0:5];
localparam HEAD_LEN = 6'd6;

pkt_head[0] <= 8'hAA;
pkt_head[1] <= 8'h55;
pkt_head[2] <= seq[15:8];        // 帧序号高字节
pkt_head[3] <= seq[7:0];         // 帧序号低字节
pkt_head[4] <= 16'd512 >> 8;     // 点数高字节
pkt_head[5] <= 16'd512 & 8'hFF;  // 点数低字节

// tx_byte_num 改成 1024 + 6 = 1030
tx_byte_num <= 16'd1030;
seq <= seq + 1'b1;               // 每包序号 +1
```

**上位机这边一行都不用改** —— `AScanProtocol.Parse` 已经能自动识别这种格式,
并且会去读序号。加完之后,上位机就能精确算出丢包率了。

### 7.2 换成真实的超声波采集数据

现在 `data_gen` 发的是 `0~511` 的自增数。把生成逻辑换成你的真实采集结果即可,
格式保持不变:**每 2 个 16 位点打包进一个 32 位字,只发前 1024 字节。**

> 顺便提一句:你现在 `tx_mem` 声明的是 512 个 32 位字(2048 字节),
> 但只发前 1024 字节,后一半是浪费的。如果确定只要 512 个点,
> 把 `tx_mem` 改成 `[0:255]` 更省 BRAM。

### 7.3 加数据保存和历史回放

把每一帧写进 SQLite 数据库,再加一个"按时间段查询回放"的功能。
这是从"演示程序"变成"能交付的检测设备"的关键一步。

### 7.4 加闸门(Gate)功能

超声波检测里的标准功能:在深度轴上划一个区域,只在这个区域里找峰值。
这样可以避开表面波和底面波的干扰,专注看缺陷。界面上就是两条可拖动的竖线。

### 7.5 加报警阈值

峰值超过某个值、或者峰值出现在某个深度范围内,就记录一条报警。
可以配合 7.3 存进数据库,形成检测报告。
